# Network protection

The integration works with ordinary LAN access and does not require a particular router. **I strongly recommend blocking matrix internet access and isolating this legacy firmware from trusted devices.** Installing an integration alone does not secure the box.

## Recommended: enforced firewall and VLAN

Use a dedicated device VLAN or equivalent switch-enforced isolation. Permit only:

- Approved controllers → matrix TCP 80, with stateful replies.
- Matrix → HA UDP 8811, with a verified method of delivering the packets across the chosen topology.
- Optional matrix → local cloud/monitoring listeners, using only configured ports.
- Only the local DHCP/DNS infrastructure actually needed.

Deny other routed traffic to the internet, internal networks, VPNs and gateway management services. **Use REJECT rather than DROP for the matrix's outbound traffic.** A matrix whose DNS and cloud connections were silently dropped ran out of buffers while waiting on them and hit a bus fault (see the captured crash analysis in the [heap overflow finding](CEC-HEAP-OVERFLOW.md)). A reject makes those connections fail fast instead of hang. Cover **IPv4 and IPv6**. Deny by source network/interface where possible: a source-IP or MAC-only rule is weaker against a compromised device spoofing its identity. Verify fresh connections after provisioning; existing connection-tracking state may retain an earlier NAT mapping.

A subnet broadcast does not become routed unicast just because a firewall permits its port. Arrange a HA interface on that network or a tightly scoped UDP relay, and verify it. Do not enable general multicast/broadcast reflection to solve one service.

If redirecting manufacturer connections, retain the WAN deny. A manufacturer address can change; a narrow redirect should then fail closed. Same-subnet hairpin redirects can require source NAT, otherwise the local server's reply can bypass the gateway and break the original TCP connection.

## Basic fallback: static IPv4 with no working gateway

For someone without configurable firewalling, this can stop ordinary off-subnet traffic generated by unmodified firmware. It does not require a special HA integration feature.

1. Put HA and the matrix on the **same IP subnet**. Give the matrix a stable manual IP and the correct subnet mask. Exclude its static address from the router's dynamic DHCP pool.
2. Leave the default gateway empty, or use `0.0.0.0`, **if the matrix accepts that**. These exact settings have not been live-tested on the development unit.
3. If the firmware requires a gateway address, choose a genuinely unused address **inside that subnet**, reserve/exclude it from DHCP, and make sure no router or other host owns it. Do not copy a numerical example without checking your network.
4. Clear external DNS resolvers if the firmware permits it. If a local resolver is needed, restrict its answers rather than allowing unrestricted recursive DNS. DNS can otherwise provide an indirect path to the internet even when ordinary WAN routing is blocked.
5. Disable IPv6 on the matrix, or separately block its IPv6 egress, if supported. An IPv4 gateway setting does not disable IPv6 router advertisements/default routes.
6. Check that HA still reads/controls it and receives new UDP packets. Check at the actual router/WAN edge that no matrix traffic is leaving. A failed ping by itself is insufficient.

Keep a record of the original network settings and physical recovery access before changing them. If HA or management clients are on a different subnet, an absent gateway can prevent replies and lock you out until you reconnect locally.

An unused gateway generally causes ARP retries instead of sending the original traffic off-subnet. Firmware can continue trying; it is not guaranteed to stop making attempts internally. A device with a deliberately malicious network stack could use another router it discovers on the local Ethernet segment. Other LAN devices remain exposed.

### Why not use HA as the gateway?

HA's ordinary web server is not a router or transparent proxy. Setting the gateway to HA only prevents normal off-subnet traffic if that host does not forward packets; a host with IP forwarding/NAT enabled might forward them. It does not automatically deliver the manufacturer's HTTP requests to the integration's monitoring listener. Explicit routing, NAT or proxy configuration is required for that, with its own enforced deny rules.

A genuinely unused address is the clearer basic fallback. Configuring the optional native **cloud destination** directly to HA's IP and its listener port is a different setting and can work on the same subnet without any default route. It still does not redirect the separate firmware-monitoring HTTP channel.

## Limits of the integration

The legacy UDP/cloud protocols are not cryptographically authenticated. Matching source addresses, serials or device headers helps avoid accidental cross-device association but cannot defeat a malicious LAN peer. The optional listeners do not implement firmware downloads and always decline updates, but that does not patch the manufacturer's firmware. Restrict access to HA, the matrix HTTP API and any optional listener ports. The known firmware can accept some controls without admin authentication; changing the web UI password is not a substitute for isolation.

Technical background: [IPv4 host routing requirements, RFC 1122](https://www.rfc-editor.org/rfc/rfc1122.html), and [IPv6 router discovery, RFC 4861](https://www.rfc-editor.org/rfc/rfc4861.html).

## HA-owned update metadata checks

Daily advisory checks use HA internet access; the matrix WAN deny remains in place. Disable firmware checks in integration options for fully offline operation. The vendor endpoint uses HTTP and receives matrix serial, model, vendor, application version and hardware family. The collector still always responds Update=false to the matrix. HA never forwards a vendor UpdateURL to the device and never fetches an image. A firmware notification is not proof of image authenticity.
